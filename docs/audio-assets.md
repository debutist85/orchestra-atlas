# Audio assets

Master WAV stems and derived AAC files are two products of the same recording. They are generated by separate pipelines and must stay independent.

```text
                 master WAV
                    │
          ┌─────────┬─────────┐
          ▼         ▼         ▼
     activity   whole AAC   stem chunks
          │         │         │
          ▼         ▼         ▼
   activity.json  *.m4a    chunks/{stem}/000.m4a
```

`full_orchestra.wav` is chunked like every other stem (stem id `full_orchestra`), so the player schedules all audio on one clock. The whole-file AAC from `audio:encode` is not loaded by the player.

## Master WAV files

Masters are the source of truth for a repertoire excerpt. They are exported together from the notation/DAW project so every stem shares one musical timeline.

- Location: `public/audio/{excerpt-id}/stems/raw/`
- Catalog: `stemDirectory` on the excerpt in `src/features/listening/excerpt.ts`
- Purpose: activity analysis and encoding. Playback loads the derived AAC files.

Never modify, overwrite, normalize, trim, rename, or delete a master WAV in place.

These files are large (gigabytes per excerpt) and are gitignored under `public/audio/**`.

## AAC web stems

AAC (`.m4a`) files are derived web assets. Each file keeps the WAV basename so the source is obvious (`cello.wav` → `cello.m4a`). The format was Opus (`.opus`, Ogg container) until it was found to silently fail on Safari/iOS — Safari's media stack has no Ogg demuxer, regardless of codec support. AAC in an MP4/M4A container is universally supported by every Safari/iOS version, at the cost of somewhat larger files than Opus achieved at the same bitrate.

- Location: `public/audio/{excerpt-id}/stems/opus/` (directory name predates the AAC switch; it holds `.m4a` files)
- Catalog: `opusDirectory` on the excerpt, or a sibling `opus` folder when masters live in `raw`
- Purpose: web playback

Encoding copies channel layout and does not apply gain, dynamics, fades, silence removal, or tempo changes. That is not a musical edit, and stems are not independently trimmed to “fix” container duration.

Decoding a whole AAC file into an `AudioBuffer` still expands it to PCM in memory.

## Playback architecture

- `chunks/full_orchestra/000.m4a` — the full-mix bed, in 15-second chunks. It plays whenever the transport runs and stays (ducked) under family/instrument focus.
- `chunks/{stem-id}/000.m4a` — synchronized 15-second focus stems layered on top of that bed. The engine schedules the bed and the stems through `src/features/listening/chunk-scheduler.ts` on one AudioContext clock.
- `activity/{excerpt}.gain.runtime.json` — lossless gain runtime retaining the analysis source's instrument/shared/orchestra envelopes and sample interval, plus gates, onsets and chunk flags. The current source uses 10 ms samples. The scheduler uses only the raw-peak chunk mask to skip digitally silent chunks. The separate visual runtime uses 20 ms samples. `npm run audio:compact` creates both runtime files and compressed sidecars without overwriting the analysis source. Development loads the local gain runtime; production loads its Brotli-encoded R2 object. Detailed analysis and the legacy profile remain offline source/review assets rather than startup requests. See [activity review](activity-review.md#compact-visual-runtime-profile).

The current excerpt provides one pre-mixed WAV per instrument and one per supported family (`strings.wav`, `woodwinds.wav`, and `brass.wav`). Family and instrument selection therefore schedules one focus stem; the player never sums stems at runtime, so every family with instruments needs its own premix. `audio:chunks` and `audio:activity` fail until one exists. `timpani.wav` serves both the current percussion family and instrument selection.

Initial repertoire load fetches the chunk manifest and activity profile, then decodes the bed chunk under the playhead. Once playback starts, the scheduler speculatively warms the next navigation choices: the family mixes from orchestra view, or the current family's instrument mixes from a family or instrument view. The audible selection itself is always one pre-mixed stem. Whole-file `{stem}.m4a` files may still exist beside the mix as encoder output; the player never loads them.

Playback behavior is specified in [specs/listening.md](../specs/listening.md).

## Commands

FFmpeg (with its native AAC encoder — present in essentially every build, no special flag required), plus **ffprobe**, must be on `PATH`.

Encode the current excerpt (Beethoven 7 II) at the default **96k** bitrate:

```bash
npm run audio:encode
```

Encode a specific excerpt:

```bash
npm run audio:encode -- beethoven-7th-2nd
```

Force regeneration, compare another bitrate, or encode one stem:

```bash
npm run audio:encode -- beethoven-7th-2nd --force
npm run audio:encode -- beethoven-7th-2nd --bitrate 128k
npm run audio:encode -- beethoven-7th-2nd --file cello.wav
```

Up-to-date AAC files (newer than their WAV) are skipped unless `--force` is passed. Existing outputs that fail validation are encoded again.

Cut every stem, including `full_orchestra.wav`, into synchronized 15-second AAC chunks:

```bash
npm run audio:chunks -- beethoven-7th-2nd
npm run audio:chunks -- beethoven-7th-2nd --force
npm run audio:chunks -- beethoven-7th-2nd --file flute.wav
```

Chunks are written to `public/audio/{excerpt-id}/stems/chunks/{stem-id}/000.m4a` from the WAV masters, not from the existing whole-file AAC. Every stem uses the same sample-accurate boundaries, and each chunk holds exactly its slot's samples (the player clips sources to the slot, so a missing sample would click at the join). A `manifest.json` in that folder describes duration, chunk length, and stem IDs.

Activity envelopes stay on the other pipeline:

```bash
npm run audio:activity -- beethoven-7th-2nd
```

## Adding another excerpt

1. Put the master WAV stems in `public/audio/{excerpt-id}/stems/raw/`.
2. Add an excerpt entry in `src/features/listening/excerpt.ts` with `id`, `title`, `stemDirectory`, `opusDirectory`, the instrument → filename map (one WAV per instrument), and `familyStems` (one premix WAV per family that has instruments; export these from the score alongside the instrument stems).
3. Run `npm run audio:encode -- {excerpt-id}`, `npm run audio:chunks -- {excerpt-id}`, and `npm run audio:activity -- {excerpt-id}`.
4. Whole-file AAC is written to `public/audio/{excerpt-id}/stems/opus/`. Stem chunks go to `public/audio/{excerpt-id}/stems/chunks/`. The activity profile is written to `public/audio/{excerpt-id}/activity/{excerpt-id}.json`.

The encoder discovers every `*.wav` in `stemDirectory`. It does not invent instrument IDs. Filenames with spaces, parentheses, or mixed capitalization are preserved.

## Reviewing analysis quality

Use `/dev/activity-review` for raw dynamics, spectral onset candidates, sounding
spans and comparison with the current profile. It can analyze local WAV masters
or clearly labelled playback files, audition onset clicks, and export reviewed
reports with source hashes. `npm run audio:review -- --help` describes offline WAV
report generation. These reports remain separate from production activity data
and chunk masks. See [Audio analysis and review](activity-review.md).
